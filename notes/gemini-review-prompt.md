# 给 Gemini 的审核与优化提示词

使用方法：把下面分隔线内的整段，粘贴给 Gemini，并把本项目文件夹（vibe-coding-constitution）作为附件 / 上下文一并给它。

---

你是一名资深的软件工程流程顾问兼文档审查专家。我有一套用来约束 AI 编程（Vibe Coding）的工程规范，存放在 `vibe-coding-constitution` 文件夹里，核心文件包括：`CONSTITUTION.md`（宪法正本）、`Docs/README.md` 与事实文档模板、`specs/SPEC-template.md`（需求规格模板）、`agents/` 下规划 / 开发 / 测试 / 审查四份 Agent 规程、`workflows/` 下 Git 流程、测试门禁、开发全流程三份文档，以及 `registry/` 项目与能力登记册、`prompts/` 启动提示词。

请你完整读完所有文件后，做一次严格审核，并按下面要求输出。你的任务是审核和提优化建议，不要直接重写整套文件。

## 审核维度（逐项给结论，不许只给总评）

1. **内部一致性**：各文件之间有没有互相矛盾、重复定义、术语不统一的地方？逐条列出，注明文件名和具体位置。
2. **完整性**：这套约束要真正落地，还缺什么？例如 SPEC 模板缺的字段、测试门禁缺的环节、异常与回滚处理、文档版本管理、多人 / 多 Agent 并发冲突处理等。按重要程度排序。
3. **可执行性**：哪些条款写得太空、无法被 Agent 实际执行或无法验证？给出可落地的改法示例（每条至少给一句改写示范）。
4. **冗余与负担**：哪些流程对小型脚本项目过重？请给出按项目规模分级的建议（例如小脚本 / 中型工具 / 正式产品三档，各档可裁剪哪些步骤）。
5. **风险盲区**：密钥安全、代码审查、依赖管理、数据备份、许可证等方面还有什么没覆盖的风险？
6. **对其他 AI 的友好度**：一个从未见过这套规范的 AI（如另一个编程助手）只读这套文件，能否无歧义地照着干活？哪里会让它误解？

## 输出格式

- 第一部分：问题清单表格，列：编号｜严重程度（高 / 中 / 低）｜所在文件｜问题描述｜修改建议。
- 第二部分：你认为最值得优先改的 5 处，各给一段「原文 → 改后」的对照文本，改写要保持原文的中文表达风格、简洁直接，不许写成空泛的套话。
- 第三部分：一句话总评＋这套规范目前处于什么成熟度（草案 / 可用 / 成熟，三选一并说明理由）。

## 限制

- 不要改动原文件的核心立场：文档与代码分离、产品事实单一出处、无 SPEC 不开发、开发与测试只认同一份 SPEC、主分支永远可用、密钥永不进仓。这六条只能加强，不许建议取消。
- 所有批评必须指向具体文件和具体句子，不许给「建议进一步完善」这类没有落点的意见。
- 如果某个文件你没有实际读到，直接说明缺失，不要假装读过。
